## The Measurement Trap: Why Query Engines Still Undervalue Adaptivity

Ask a database engineer what makes a query optimizer good, and the answer will almost always be framed in terms of plan quality: does the optimizer choose the right join order, the right access path, the right physical operators, given what it knows about the data. This is a reasonable question, and it has produced decades of genuinely useful research — cost models, cardinality estimation techniques, plan enumeration strategies. But it rests on a quiet and consequential assumption: that the optimizer's job is to get the plan right once, up front, before execution begins. Adaptive re-planning — the capacity of an engine to notice, mid-execution, that its assumptions were wrong and to change course — remains a secondary concern in most systems, and a secondary concern in most of the literature that evaluates them. This is a mistake, and it persists not because adaptivity is unimportant but because it is inconvenient to measure.

Static plan quality benchmarks beautifully. You can hold the query fixed, hold the data fixed, generate a plan, execute it, and compare the resulting runtime against some baseline or against an oracle plan computed by brute force. The whole apparatus of query optimization research — TPC-style benchmarks, cardinality estimation error metrics, plan diagrams — is built around this static frame. It is reproducible, it is decomposable into clean sub-problems, and it rewards the kind of incremental, publishable improvement that keeps a research area alive. None of this is true of adaptive re-planning. The value of adapting mid-query is inherently conditional: it depends on when and how badly the initial estimates were wrong, on workloads that drift over the course of execution rather than sitting still for a single cardinality estimate, on correlations that no static model captured because they only become visible once data actually starts flowing through the pipeline. You cannot easily construct a benchmark that isolates "how well does this engine recover from being wrong," because being wrong is not a parameter you control cleanly — it is an emergent property of real data interacting with a necessarily approximate model of that data.

The result is a research and engineering culture that optimizes for what it can see. Static plan quality gets the sophisticated cost models, the careful ablations, the leaderboard comparisons. Adaptive re-planning gets treated as a fallback mechanism, bolted on to catch the worst estimation failures, rarely designed with the same rigor as the planner it is meant to correct. This asymmetry in attention does not reflect an asymmetry in importance.
